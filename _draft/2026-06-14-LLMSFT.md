SFT 和预训练一样，都是在学习：给定前面的 token，预测下一个 token。而 SFT 阶段更多地把预训练模型的概率分布重新往目标行为偏移。

在完成预训练时，模型具备强大的语言理解和生成能力，但还只是一个无情 Next-Token Prediction 机器，不理解问答或指令遵从的范式；有监督的问答序列数据训练，
让模型理解以指令遵从和对话的方式安心当一只美国大豆包或者橙色章鱼，此时模型被 align 到助手的角色。

# 1. SFT 全流程

1. 数据准备与格式化：对初始预料有一个筛选过程，可能会基于规则（长度、乱码率）+ 基于模型（困惑度打分）筛选；然后将原始的指令和回答拼接成特定 Chat Template。
2. 标签掩码（Label Masking / Target-only Loss）：在计算 Loss 时，只对模型的 Response 部分计算 Loss，而对输入的 Prompt 进行 mask（通常设为 -100），避免模型去“预测”输入本身。
3. 动态填充与 Batch 组装：在同一个 Batch 内对不同长度的文本进行 Padding，并设置相应的 attention_mask。
4. 模型加载与高效微调配置：加载预训练模型，并引入 PEFT（如 LoRA）以节省显存。
5. 前向传播与反向传播循环：通过自回归（Autoregressive）方式计算交叉熵损失，并更新模型参数。


从数学上看, SFT （仍然）在做：$\max_{\theta}\sum \log P_{\theta}(y_t|x,y_{\lt t})$

其中：$x$ 是 Prompt，$y$ 是 Answer

# 2. SFT 如何能改变模型行为

大量问答对样本累计后，对应回答 token 出现概率提升，导致整个回答风格发生迁移。

因此，SFT 的本质是**对条件概率分布进行局部重塑**。


# 3. SFT Loss是什么

本质就是 Cross Entropy。

设真实 token：$y_t$，模型输出 logits：$z_t$，softmax：$p_t=\text{softmax}(z_t)$

loss：
$$
L=-\sum_t \log p_t(y_t)
$$

或者平均：

$$
L=-\frac1N\sum_t \log p_t(y_t)
$$


---

通常情况下，我们不会计算 User/System/Observation 部分的 loss，他们的Label会被打成 -100。否则模型会尝试学习用户输入的内容，属于一种无意义推测了。

另外，User部分 mask，Assistant部分 unmask 被称为 Completion-Only SFT。现代模型会用 Special Token 把他们分割好，在训练框架中处理。 

即：

$$
L=-\sum_{t\in assistant}\log P(y_t)
$$

对 Agent 轨迹，尤其是非主流输出的内容，得自己把 Thought, Action 等相应标记好算 loss, observation 不算。

# Teacher Forcing 和 Exposure Bias

SFT最大特点是 Teacher Forcing。即永远喂真实历史，$P(y_t|y_{<t}^{gold})$。

而不是：$P(y_t|\hat y_{<t})$
---

Teacher Forcing带来的经典问题是推理的时候如果不小心在预测token的过程中，预测出了和训练数据不同的token，这里的生成错误导致后续的输入也发生改变，导致训练和推理分布不一致 $P_{train}\neq P_{infer}$ ，即 Exposure Bias。

这也是后来 RLHF、DPO、RFT 出现的重要原因之一。

# 九、长序列SFT的特殊问题

对于你的Agent轨迹（80k token）尤其重要。

## Loss Dilution

假设：

```text
前面79000 token
后面1000 token
```

真正重要的是最后：

```text
Final Answer
```

但loss平均：

[
L=\frac1N\sum l_t
]

则：

Final部分梯度被稀释。

---

常见做法：

### 加权Loss

[
L=
\sum w_t l_t
]

例如：

```text
Thought      0.2
Action       1.0
Final Answer 3.0
```

提高最终答案权重。

很多团队会发现：



对于 Agent 数据尤其如此：

谢谢你的反馈。我同意，对于已经参与模型训练的人来说，过多的项目符号和代码块会打断逻辑链条。真正有价值的内容应该像一篇技术讲义，而不是培训 PPT。那我尝试用更连贯的方式重新组织一下预训练的原理，并把一些通常被简化掉的关键点补充进去。

从机器学习的角度看，今天的大语言模型预训练实际上是在解决一个极其简单的问题：给定一个 token 序列 (x_1,x_2,\dots,x_n)，学习其联合概率分布

[
P(x_1,x_2,\dots,x_n)
]

由于直接建模联合分布非常困难，根据概率链式法则，我们把它分解为：

[
P(x_1,x_2,\dots,x_n)
====================

\prod_{t=1}^{n}
P(x_t|x_{<t})
]

于是训练目标就变成了学习每一个条件概率 (P(x_t|x_{<t}))。这就是所谓的 Next Token Prediction。无论是 GPT-4、Claude、Qwen 还是 Llama，其预训练目标本质上都没有脱离这个框架。

很多初学者看到这里会产生一个疑问：如果训练目标只是预测下一个词，那么模型为什么会学会数学、代码、推理、规划甚至某种程度上的常识？这实际上是预训练最核心的地方。

假设你想预测一句话中的最后一个词：

“牛顿发现了______定律。”

如果模型想提高预测准确率，它必须知道牛顿是谁，什么叫发现，什么叫定律，以及历史上哪些定律与牛顿有关。如果它不知道这些知识，它就无法降低 loss。因此，预测任务虽然表面上是在预测 token，但从优化的角度看，它被迫建立一个能够解释数据生成过程的内部表示。换句话说，模型并不是主动学习知识，而是在降低预测误差的过程中被迫构建知识。

这也是为什么很多研究者更喜欢把 LLM 理解成一种世界模型（World Model）而不是知识库。参数里存储的并不是一条条事实，而是一套能够生成这些事实的统计结构。

训练过程中，Transformer 通过反向传播不断调整参数。设模型参数为 (\theta)，训练数据集为 (D)，则最大似然目标可以写成：

[
\max_\theta
\sum_{x \in D}
\sum_t
\log P_\theta(x_t|x_{<t})
]

对应的损失函数是交叉熵：

[
L
=

-\frac1N
\sum_t
\log P_\theta(x_t|x_{<t})
]

对于训练工程师来说，一个重要的认识是：预训练并不直接优化“知识”“推理”或者“智能”，它只优化交叉熵。所有高级能力最终都必须通过“降低交叉熵”这一条路径间接产生。如果某种能力不能帮助模型更好地预测未来 token，那么梯度下降就没有理由学习它。

接下来需要理解 Transformer 在这里扮演什么角色。Attention 机制的出现，本质上解决的是长期依赖问题。传统 RNN 很难利用几千个 token 之前的信息，而 Transformer 允许当前位置直接访问上下文中的任意位置。其核心公式为：

[
Attention(Q,K,V)
================

softmax
\left(
\frac{QK^T}{\sqrt d}
\right)V
]

这里的含义并不神秘。对于当前 token，模型首先计算它与历史所有 token 的相关性，然后根据相关性加权聚合历史信息。经过大量训练后，不同的 Attention Head 会逐渐形成专门化功能。有些 Head 负责代词指代，有些负责括号匹配，有些负责代码结构，有些负责数学符号关系。这些现象已经被大量 Mechanistic Interpretability 研究观察到。

真正有趣的地方在于，当参数规模和数据规模持续增长时，模型内部会逐渐形成越来越抽象的表示。早期层可能学习词法和语法，中间层学习概念和实体关系，高层则学习更复杂的抽象结构。这种层级表示与人脑皮层中从低级特征到高级语义的处理方式有一定相似性，虽然两者机制完全不同。

从训练工程的角度看，预训练最重要的问题其实不是模型结构，而是数据分布。因为模型学到的不是“真理”，而是数据中的统计规律。如果某类模式在数据中占比更高，模型就会更倾向于学习它。例如一个模型如果训练语料中代码占 30%，另一个模型代码只占 5%，即使参数量完全相同，它们的代码能力也会有巨大差异。今天很多开源模型之间的性能差距，很大程度上来自数据配方（Data Mixture）而不是架构创新。

这也是为什么现代预训练越来越强调数据工程。预训练团队花费大量时间进行去重、质量过滤、文档分类和数据配比，并不是因为这些工作很优雅，而是因为数据分布最终决定了模型学到什么样的世界模型。对于一个 70B 参数模型而言，如果训练数据中几乎没有高质量数学证明，那么它几乎不可能凭空涌现出很强的数学推理能力。

进一步说，预训练实际上存在一种知识压缩过程。假设一个 70B 模型使用 bfloat16 存储，其参数容量大约只有 140GB。但它可能阅读了十几万 GB 的文本数据。这意味着模型不可能逐字记忆训练集，而必须把大量冗余信息压缩成更抽象的结构。因此我们看到模型能够泛化到从未见过的问题。它记住的不是具体句子，而是生成这些句子的底层规律。

在大规模训练中，还有一个极其重要的经验规律叫 Scaling Law。研究者发现，当参数量、数据量和训练计算量同步增加时，训练损失会按照幂律下降，大致满足：

[
L(C)
====

A C^{-\alpha}
+
B
]

其中 (C) 是计算预算。这意味着模型性能不会突然饱和，而是持续改善，只是边际收益越来越低。这一发现极大改变了整个行业的发展方向，因为它说明堆算力、堆数据、堆参数并非盲目行为，而是一种有理论依据的工程路线。

后来 DeepMind 的 Chinchilla 工作进一步发现，很多模型实际上处于“参数过多、数据不足”的状态。对于固定计算预算而言，适当减小模型规模、增加训练 token 数量，反而可以获得更好的结果。这也是为什么现代模型越来越重视数据量，许多模型的预训练 token 已经达到十万亿级别。

如果把整个 LLM 训练流程放在一起理解，我认为最准确的认知框架是：预训练阶段负责建立压缩后的世界模型，使模型能够理解语言、知识和现实世界中的统计结构；SFT 阶段负责把这个世界模型转换为符合人类期望的行为模式；而 DPO、RLHF、GRPO、RFT 等后训练阶段，则是在行为空间中进一步优化偏好、推理和决策能力。

因此，对于真正参与训练的人来说，预训练最值得深入理解的其实不是“预测下一个 token”这句话本身，而是三个更深层的问题：第一，为什么仅靠预测 token 就能形成世界模型；第二，数据分布如何决定最终能力边界；第三，梯度下降为什么会在超大规模参数空间中自发形成抽象表示。这三个问题至今仍然是大模型研究最核心、也最有趣的部分。



在大型语言模型（LLM）的生命周期中，**有监督微调（Supervised Fine-Tuning, 简称 SFT）**是承上启下的关键阶段。它承接了预训练阶段（Pre-training）获得的强大基座能力，通过高质量的“指令-回答”数据，训练模型理解人类指令并学会以符合人类习惯的方式进行对话。

作为负责模型训练的机器学习工程师（MLE），在 SFT 阶段不仅需要关注模型指标，更需要深入掌握数据处理、模型配置、计算效率及常见陷阱等技术细节。以下是 SFT 阶段的详细过程以及需要掌握的核心技术细节：

---

### 一、 SFT 的核心流程

SFT 的整体流程可以概括为以下五个步骤：

```text
[数据准备与清洗] ──> [Chat Template 格式化] ──> [损失计算掩码 (Loss Masking)] ──> [训练执行与分布式加速] ──> [多维度评估]
```

---

### 二、 MLE 需要掌握的关键技术细节

#### 1. 数据准备与格式化（Data Preparation & Formatting）
数据质量直接决定了 SFT 的效果，业内常说“Garbage in, garbage out”。
*   **质量重于数量（Quality > Quantity）：**
    *   根据 LIMA 等研究，几千到上万条高质量、多样化的专家编写数据，其效果往往优于数十万条低质量或机器自动生成的嘈杂数据。
    *   **实践建议：** 建立严格的数据过滤管线，去除重复、语法错误、格式混乱和带有偏见的数据。
*   **Chat Template（对话模板）的一致性：**
    *   原始数据通常是结构化的（如 JSON）。在输入模型前，需要将其转换为带有特殊标记（Special Tokens）的单文本字符串。
    *   目前主流的模板有 ChatML、Llama-3 模板等。例如：
        ```text
        <|im_start|>system
        你是一个有用的助手。<|im_end|>
        <|im_start|>user
        请解释什么是SFT。<|im_end|>
        <|im_start|>assistant
        SFT是有监督微调...<|im_end|>
        ```
    *   **关键陷阱：** **训练和推理阶段的 Chat Template 必须完全一致。** 即使只是多了一个空格或换行符，也可能导致推理时模型输出异常、重复或拒绝回答。建议在训练和推理代码中统一使用 Hugging Face 的 `tokenizer.apply_chat_template`。

#### 2. 损失计算掩码（Loss Masking / Instruction Masking）
这是 SFT 训练中最容易出错但极其重要的技术细节。
*   **原理：**
    在自回归（Autoregressive）训练中，我们不希望模型去“预测”用户的输入指令（Prompt），而只希望它“预测”助手的回答（Response）。
*   **实现方式：**
    *   在 PyTorch 的 `CrossEntropyLoss` 中，通常将不需要计算损失的 Token 的 label 设为 `-100`（PyTorch 默认在计算交叉熵时忽略值为 `-100` 的 label）。
    *   **操作细节：** 将 System Prompt 和 User Input 对应的 Token Labels 全部设为 `-100`，只保留 Assistant Response 对应 Token 的真实 Token ID。
    *   如果不对 Prompt 进行掩码，模型在训练时会试图预测用户会问什么，这会导致模型在实际应用中更倾向于模仿用户的语气或产生语序混乱，而不是直接回答问题。

#### 3. 样本拼接（Sample Packing）
*   **问题：** 不同的对话样本长度差异很大。如果简单地将它们 Padding（填充）到最大长度（如 4096），会导致显存中存在大量的 Padding Token（如 `<pad>`），浪费计算资源。
*   **解决方案：** 
    *   采用 **Packing** 技术，将多个短样本拼接成一条达到最大长度（如 4096）的长样本，中间用 EOS（End of Sequence）Token 隔开。
    *   在注意力计算时，需要配合 **Block Diagonal Attention（块对角注意力）**，防止样本 A 的输入关注到同一个拼接序列中样本 B 的内容。主流框架如 Hugging Face TRL 库中的 `SFTTrainer` 提供了 `packing=True` 选项。

#### 4. 参数高效微调（PEFT）与全量微调（Full FT）的权衡
在实际项目中，需要根据资源和算力选择微调策略。
*   **Full Fine-Tuning（全参数微调）：**
    *   **优点：** 模型的拟合上限最高，适合复杂的指令遵循或领域垂直深耕。
    *   **缺点：** 显存消耗极大，容易发生**灾难性遗忘（Catastrophic Forgetting）**（即模型丢失了预训练阶段学到的部分通用知识）。
*   **LoRA / QLoRA（低秩适应）：**
    *   **优点：** 只训练旁路矩阵（如 $A$ 和 $B$），显存占用极小，适合资源有限的场景。
    *   **关键超参数配置：**
        *   `r` (Rank): 通常设置为 8 到 64。如果任务较复杂，可适当增大。
        *   `lora_alpha`: 通常设置为 $2 \times r$。
        *   `target_modules`: **不要只微调 `q_proj` 和 `v_proj`**。研究表明，将 LoRA 应用于所有线性层（包括 `k_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`）可以获得更接近全量微调的效果。

#### 5. 核心超参数的调试（Hyperparameter Tuning）
SFT 对超参数比较敏感，以下是常见的经验范围：
*   **学习率（Learning Rate, LR）：**
    *   全参数微调：通常设得很小，一般在 `5e-6` 到 `2e-5` 之间。过大会破坏预训练权重。
    *   LoRA 微调：学习率可以稍大，一般在 `1e-4` 到 `3e-4` 之间。
    *   **Scheduler：** 推荐使用带 Warmup 的 Cosine 学习率衰减策略（Cosine Annealing）。
*   **Batch Size：**
    *   全局 Batch Size（Global Batch Size）通常在 128 到 512 之间。可以通过 Gradient Accumulation（梯度累积）来调整，以适应单卡显存限制。
*   **Epoch 数量：**
    *   通常只需要 **1 到 3 个 Epoch**。SFT 阶段极易过拟合。过多的 Epoch 会导致模型丧失泛化能力，回答变得机械化和单一。

#### 6. 基础设施与分布式并行
*   **精度选择：** 强烈建议使用 **BF16**（Bfloat16），如果显卡支持（如 Ampere 架构及以上的 A100, H100 等）。相比于 FP16，BF16 的动态范围更大，不容易发生溢出（Overflow/Underflow），训练更稳定。
*   **显存优化技术：**
    *   **Gradient Checkpointing（梯度检查点）：** 用时间换空间。不保存前向传播的所有激活值，而在反向传播时重新计算，能显著降低显存占用。
    *   **FlashAttention-2 / FlashAttention-3：** 必须启用的算子优化，可成倍提升计算速度并降低 Attention 机制的显存开销。
    *   **分布式框架：** 常用 DeepSpeed（ZeRO-2 或 ZeRO-3）、FSDP（PyTorch Fully Sharded Data Parallel）或 Megatron-LM（适合超大规模模型）。对于中等规模模型（如 7B - 70B），DeepSpeed ZeRO-3 是MLE最常用的选择。

#### 7. 评估与避坑指南（Evaluation & Caveats）
*   **不健康的 Loss：** 
    不要盲目追求极低的验证集 Loss。如果 Loss 接近于 0，通常意味着模型对特定的模板或话术产生了严重的过拟合，在实际对话中其表现可能极差。
*   **EOS Token 丢失问题：**
    在数据处理时，确保每个 Assistant 回答的末尾都添加了 `<eos>`（End of Sequence）Token，并且该 Token 参与了 Loss 计算。如果模型没有学会何时输出 `<eos>`，在实际推理时它会喋喋不休，直到达到最大长度限制。
*   **多维度评估机制：**
    *   *自动评估（Benchmark）：* 如使用 MMLU、GSM8K 等测试基础能力是否退化。
    *   *LLM-as-a-Judge（大模型充当裁判）：* 使用 GPT-4 或更强的模型对微调后的模型输出与 baseline 进行 Pairwise（成对）对比，给出评分。
    *   *人工评测（Human Evaluation）：* 针对特定业务场景，制定详尽的标注指南进行盲测（Double-blind test）。

### 总结
作为一名机器学习工程师，在 SFT 阶段不仅要写好训练脚本，更要像数据科学家一样去**审视数据结构与 Mask 细节**，像系统工程师一样去**压榨 GPU 的算力和显存**。保持训练与推理在格式、标记上的一致性，是确保模型平稳落地的关键。

在大型语言模型（LLM）的训练中，**Shift Right（右移）**并不是一个复杂的“算法”，而是一种**核心的数据对齐操作**。它的核心目的是**确保自回归（Autoregressive）模型在预测时遵循因果性（Causality）**，即“只能根据当前及历史的 Token，去预测下一个 Token”。

根据模型架构的不同（Decoder-Only 或 Encoder-Decoder），Shift Right 的具体实现方式和所处的 SFT 阶段也有所不同。

---

### 一、 Shift Right 的两种具体实现

#### 1. Decoder-Only 架构（如 LLaMA, GPT, Qwen 等主流模型）
在目前最主流的 Decoder-Only 模型中，Shift Right 主要体现在**损失计算时的错位对齐**。

*   **原理：**
    自回归模型在位置 $t$ 输出的概率分布（Logits），对应的是对位置 $t+1$ 处 Token 的预测。
    若输入序列为 `[T0, T1, T2, T3]`，模型的前向传播会输出 4 个位置的预测 Logits：
    *   `Logits[0]`（由 `T0` 产生）用来预测 `T1`
    *   `Logits[1]`（由 `T0, T1` 产生）用来预测 `T2`
    *   `Logits[2]`（由 `T0, T1, T2` 产生）用来预测 `T3`
    *   `Logits[3]`（由整个序列产生）没有下一个真实的标签（`T4`）可以对比。

*   **对齐操作：**
    为了计算交叉熵损失（Cross-Entropy Loss），我们需要将预测值（Logits）与真实标签（Labels）进行对齐：
    *   舍弃 Logits 的最后一个位置（因为没有对应的真实标签可预测）。
    *   舍弃 Labels 的第一个位置（因为没有输入可以用来预测第一个 Token）。
    
    在 PyTorch 代码中，这一步通常表现为：
    ```python
    # 舍弃 logits 最后一个位置，舍弃 labels 第一个位置
    shift_logits = logits[..., :-1, :].contiguous()
    shift_labels = labels[..., 1:].contiguous()
    
    # 计算损失
    loss = loss_fct(shift_logits.view(-1, shift_logits.size(-1)), shift_labels.view(-1))
    ```

#### 2. Encoder-Decoder 架构（如 T5, BART 等 Seq2Seq 模型）
在这种架构中，Shift Right 指的是**构建解码器输入（Decoder Input IDs）**的过程。

*   **原理：**
    Decoder 训练时也需要因果掩码。为了预测 Target 序列 `[T1, T2, T3]`，Decoder 的第一步输入不能是 `T1`（否则会发生数据泄露），而必须是一个起始符（如 `<bos>` 或 `<pad>`），然后逐步把真实的 Label 向右移动一格输入给 Decoder。

*   **对齐操作：**
    将原始 Target 整体右移一格，最前面补上一个起始符。
    例如，Label 是 `[A, B, C]`：
    右移后变为 `[<bos>, A, B]`，这部分作为 `decoder_input_ids` 喂给 Decoder。
    
    在 Hugging Face 源码中，通常通过 `shift_tokens_right` 函数实现：
    ```python
    def shift_tokens_right(input_ids: torch.Tensor, pad_token_id: int, decoder_start_token_id: int):
        shifted_input_ids = input_ids.new_zeros(input_ids.shape)
        # 将 input_ids 整体向右移动一位
        shifted_input_ids[:, 1:] = input_ids[:, :-1].clone()
        # 最前方填入解码器开始标记
        shifted_input_ids[:, 0] = decoder_start_token_id
        return shifted_input_ids
    ```

---

### 二、 它用在 SFT 的哪个阶段？

在大模型 SFT 训练的完整流水线中，根据你使用的模型架构，Shift Right 发生在不同的阶段：

#### 阶段 A：数据整理与前向传播构建阶段（Data Collator / Forward Input Preparation）
*   **适用架构：** **Encoder-Decoder 架构**（如 T5, BART）。
*   **具体过程：**
    在 DataLoader 拼装 Batch 数据的阶段（Data Collator），或者在模型 `forward` 的最开始阶段。
    代码会将原始 `labels` 经过 `shift_tokens_right` 处理，生成 `decoder_input_ids`，然后将 `input_ids`（Encoder 的输入）、`decoder_input_ids`（Decoder 的输入）和 `labels` 一并送入模型进行训练。

#### 阶段 B：前向传播结束与损失计算阶段（Post-Forward / Loss Calculation）
*   **适用架构：** **Decoder-Only 架构**（如 LLaMA, Qwen 等主流大语言模型）。
*   **具体过程：**
    这是最常见的情况。此时，Data Collator 阶段并不会做右移操作。
    1. 你的输入 `input_ids`（包含 Prompt 和 Response）被直接送入模型，执行前向传播（Forward Pass），得到 `logits`。
    2. 在**计算 Loss 的那一刻**，代码会在显存中对 `logits` 和 `labels` 执行 `[:-1]` 和 `[1:]` 的切片操作（即上面提到的错位对齐）。
    3. 对齐后，再通过带有掩码的 Cross Entropy（如忽略标签为 `-100` 的 Prompt 部分）计算出最终的 SFT 损失并进行反向传播。

---

### 三、 作为 MLE 需要注意的关键细节

1.  **`-100` 的处理：**
    在 SFT 中，我们通常会把 Prompt 部分的 Label 设为 `-100`。在做 `labels[:, 1:]` 切片时，对应的 `-100` 位置也会发生相应的右移，这由 PyTorch 的切片机制天然保证，但手动实现自定义 Loss 时务必注意不要把对齐顺序弄反。
2.  **验证集评估（Evaluation）时的一致性：**
    在评估模型验证集 Loss 时，必须使用与训练阶段**完全相同**的 Shift 逻辑，否则算出来的困惑度（Perplexity, PPL）或 Loss 会出现偏差，导致无法准确评估模型性能。
3.  **Hugging Face 自动处理：**
    大多数主流的 Hugging Face 预训练模型（如 `LlamaForCausalLM`）在它们的 `forward` 函数内部**已经自动写好了**针对 Decoder-Only 的 `shift` 逻辑。如果你直接将 `labels` 传给模型，模型会在内部完成错位对齐并直接返回 Loss；但如果你提取出 `logits` 自己手动写 Loss 计算，或者在使用某些自定义并行框架时，则需要你手动编写 `logits[..., :-1, :]` 和 `labels[..., 1:]` 的对齐逻辑。
